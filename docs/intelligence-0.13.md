# xSERA 0.13 분석 엔진 적용 계약

다섯 개발 범위를 수집 ACK 뒤에 실행되는 분석 계층과 운영 콘솔에 연결한다.
기존 원본, 수집 영수증, v3 필드, tenant/index 권한 및 대응 승인 계약을 유지한다.

1. 추가 v4 보안 필드는 생성·관찰·수집 시각을 구분하고 장치·부팅·컨테이너·파일 버전을 알 수 없을 때 추측하지 않는다. OCSF 1.4.0 매핑은 파생 데이터다. 고정 Shadow는 원본·영수증·파서·출처·정책·identity/TI/baseline/model 문맥을 동결하여 순수 비교하고 재현한다. 운영 Case나 대응을 실행하지 않는다.
2. 관찰·원자 탐지·기존 기여·원본 근거가 있는 Finding·행동 이상·CPU ML·복합 탐지를 공통 신호로 저장한다. 원본 ID와 영수증 hash, 부모 신호 전체 ancestry, 규칙·문맥·모델 hash를 보존한다. 공유 원본과 같은 이상 페이지는 연결된 종속 그룹으로 처리한다. 위험 점수는 그룹별 최대 감쇠 가중치를 합산하며 악성 확률로 표시하지 않는다. Story는 보고된 프로세스 incarnation, 부모 GUID와 시작 식별자, flow, 파일 관계를 버전 이력과 함께 저장한다. 관계는 입증된 인과관계나 endpoint 대응 권한이 아니다.
3. 복합 탐지는 2~8개 긍정 입력과 entity/story/flow/process/session 결합을 지원한다. 인덱스 전체 범위·입력 selector·고정 부모 revision을 SQL에서 먼저 제한하고, 회차별 최대 256개 후보를 영속 cohort에 담는다. 2,000개를 넘는 관련 후보도 join key별 색인과 최대 256개 대안 작업의 영속 DFS bookmark로 이어서 평가한다. 중간 상태를 완료로 표시하거나 조용히 자르지 않는다. 신호당 32개 원본 ancestry와 회차별 시간·메모리 예산은 유지하며 정책도 순환 실행한다. 부모 정책 revision과 ML 모델 revision·가중치·특징 계약 pin은 서버가 생성하며 변경·비활성화된 부모는 새 검토를 요구한다. 독립 승인과 현행 권한을 재확인한다. strict 시각 순서는 알려진 precision interval이 겹치지 않을 때만 인정한다.
4. Case 병합·분할 이후 episode/Story 경로를 유지한다. 재평가는 기본 비활성이고 설정된 범위만 평가한다. 다른 사람이 검토한 제안 또는 명시적으로 허용한 동일 증거 부착만 처리한다. 승인 대기·실행 중 대응은 보존한다. 행동 특징은 실제 byte delta, 알려진 인증 결과, 명시적 파일 변화, 생성 시 부모-자식으로 제한한다. 정상 기준·시즌·peer·cold/stale/coverage와 학습 누수를 함께 표시한다.
5. CPU PyTorch autoencoder를 선택 기능으로 제공한다. 저장된 정상 학습 원본 16개 이상과 별도 holdout 8개 이상, 정상 cohort 확인과 독립 모델 승인이 필요하다. JSON 가중치와 특징 계약을 고정하고 CPU 한 thread/별도 제한된 작업자에서 실행한다. 모델 활성 상태와 승인자 권한을 추론 뒤 신호 발행 transaction에서도 재검사한다. 호환되지 않으면 `시스템에서 호환되지 않음`으로 제외하고 기본 분석은 계속한다. 악성 확률·자율 차단을 제공하지 않는다.

인덱싱 outbox와 원본·기여·Finding cursor, ML job 및 복합 cohort 상태는 SQLite에 저장한다. 원본 ACK 안에서 모델이나 그래프 작업을 하지 않는다. CPU ML 작업자는 기본 분석 작업자와 분리한다. 검토된 동일 모델·tenant·owner의 정확한 호환 인덱스별 작업을 최대 32개씩 묶고, 그 모델 그룹의 작업이 16개 이상이거나 가장 오래된 작업이 5초를 기다렸을 때 추론한다. 다른 모델의 대기 건수로 작은 배치를 시작하지 않으며 실제 서비스된 그룹을 기준으로 순환한다. 대기·선택 건수, 최초 대기 시각, 연산 시간과 작업자 전체 시간은 별도 영속 진단이다. 지연 작업의 원본과 기존 Case/hold, 시계열 버퍼·대기 작업을 용량 정리로부터 보호한다. 권한 철회나 변경된 출처는 항목별 제외 근거를 남기며 다른 항목을 막지 않는다.

관찰과 원자 처리는 회차의 선언된 정책 범위를 읽고 같은 소유자·예약된 transaction에서 원본과 영수증을 검사한다. 관찰은 복합 결정이 아니므로 사용하지 않는 복합 모델의 전체 가중치·학습 문맥을 반복 검증하지 않는다. 현행 정책 승인·owner/reviewer와 범위는 계속 확인하고, 복합 부모·모델 pin은 실제 복합 사용 시 검사한다. 큰 모델의 불변 JSON 해독·hash는 정확한 최신 원본 행 전체가 일치할 때만 내용 cache에서 재사용한다. 이는 최대 16개 모델·32MiB 직렬화 내용으로 제한하고 권한·출처·검토·활성·폐기 답변은 저장하지 않는다. 매 호출 원본 모델 행·출처·소유자·독립 검토자·활성 포인터·폐기·grants를 재확인하며 명시적인 예약 transaction memo의 경계 검사는 별도로 유지한다. 필수 승인 검증 setup 뒤 후보 처리에 별도의 유한 회차 예산을 주고, 만료된 작은 예산도 취소되지 않았다면 최소 한 후보/DFS 작업을 영속 진행시킨다. 기존 transaction 절대 기한·후보/ancestry 한도와 취소는 유지하며 총 지연은 setup을 포함한 실제 값이다.

복합 후보의 운영 만료는 실제 서버가 수집한 근거의 처리 대기열을 고려한다. 같은 tenant·정의된 전체 인덱스 범위에서 아직 처리되지 않은 원본, 관련 ML 작업·시계열 버퍼의 가장 이른 영수증 received 시각까지 후보 cutoff를 늦춘다. 마지막 지연 입력이 원자 신호가 된 직후 대기열이 비어도, 새로 만들어진 입력 selector·revision·범위에 맞는 신호의 원본 영수증을 기준으로 다음 동결 cohort에서 기존 anchor를 한 번 더 검토한다. 이 cutoff는 기존 `window_end`에 고정하여 재시작 후에도 유지한다. 원본의 보고된 과거 event timestamp나 다른 tenant/인덱스 대기열은 cutoff를 늘리지 않는다. 보고된 event-window 결합 한도·precision·32개 원본·종속 그룹·현행 승인 검사는 그대로 적용한다. 용량 정리는 대기 원본, 진행 중 cohort 및 마지막 지연 신호가 다음 capture를 기다리는 동안 관련 ancestry를 보호한다. cohort가 끝나고 관련 대기열·새 입력이 없으면 기존 TTL로 돌아가며 별도 Case/hold/모델 참조는 유지한다.

Story 부모·자식 조회는 source/account/realm, GUID·시작 식별자, device/boot/container의 보고 값을 표현식 색인으로 조회한다. 색인은 기존 저장 projection을 그대로 대상으로 생성하며 과거 결측값을 추측하거나 projection을 다시 쓰지 않는다. 늦게 도착한 부모의 자식이 1,000개를 넘어도 회차별 128개 영속 관계 작업으로 재시작 후 이어서 연결한다. alias 경로와 전체 node/edge 권한, 기존 Case 전체 범위를 다시 확인한다. 기존 신호의 당시 Story ID와 고정 Shadow 입력은 유지한다.

`GET /api/v3/intelligence/slo`는 서버 received 시간창의 허가된 원본에 대해 실제 indexing transaction, 기본 정책 분석 완료, 첫 탐지·Case·복합 탐지, AE·시계열 대기/완료 시각을 반환한다. 회차 처리 시각은 해당 영속 transaction과 함께 기록한다. 과거에 측정하지 않은 단계는 NULL이다. 50,000개 이내 cohort의 nearest-rank p50/p95, 결측·시계 역행 수와 실제 대기열을 제공하며 최대 EPS·SLA 인증으로 환산하지 않는다. 첫 observation 신호와 첫 탐지 시각은 구분하고, 기본 정책 완료는 후속 ML·복합 탐지 완료를 뜻하지 않는다.

콘솔 `신호·AI 분석`은 실제 API의 신호, Story, 정책 검토, 모델 학습/승인, Shadow 비교, 행동 분석 및 Case 제안 상태를 표시한다. 기본 서버는 새 규칙·모델을 임의 활성화하지 않는다. 별도 로그 실험에서만 정상 학습과 두 계정 승인을 수행한다.

향후 Yocto 기반 자체 xSERA OS는 기존 layer를 출발점으로 하되 대상 CPU/BSP/Python ABI에 맞는 CPU ML 패키지와 license/SBOM·오프라인·업데이트/rollback·실장비 검증이 필요하다. Windows wheel을 이미지에 넣지 않는다. 이번 변경의 OS readiness는 운영체제 이미지 빌드나 하드웨어 인증을 뜻하지 않는다. 자세한 CPU 계약은 [CPU ML runtime](CPU_ML_RUNTIME.md), Shadow 계약은 [schema/shadow](nextgen-schema-shadow.md)를 참조한다.

Vatex LUMINA xSERA 0.8 — 대량 로그 운영 및 검증 안내

이 문서는 구현 계약과 시험 방법을 설명한다. 특정 건수 또는 EPS의 통과
인증서가 아니다. 실제 통과 건수, 소스 해시, 장비, 설정, 실패 결과는 별도
qualification JSON 보고서를 확인한다. 5천만 건 보관과 5천만 건/일 수집은
서로 다른 요구사항이며 후자는 하루 평균 약 579 EPS에 해당한다.

1. 원본 검색과 전문검색을 구분한다

HTTP 수집의 durable ACK는 원본의 영속 큐 적재를 뜻한다. 이후 DuckDB 원본
색인이 완료되어 시간·테넌트·인덱스·호스트·구조화 필드 검색이 가능해진다.
전문검색은 별도의 로컬 SQLite FTS5 캐시이며, 원본 색인 시 같은 제어
트랜잭션에 기록한 영속 journal을 백그라운드에서 작은 배치로 처리한다.
전문검색 질의마다 전체 원본의 이벤트 ID를 다시 스캔하지 않는다.

원본과 FTS 사이의 처리 중 상태, 삭제 대기, 원본 커밋 후 ACK 이전 상태는
정확한 결과를 가장하는 대신 전문검색을 일시 거부한다. FTS 캐시는 다른
노드로 복제하는 제어 상태가 아니다. 각 노드에서 로컬 원본을 기준으로
구축하며, 캐시 상태를 데이터 복제 또는 고가용성 검증으로 해석하지 않는다.

로그 관리 화면의 전문검색 상태:
  ready              현재 원본과 삭제 세대까지 적용 완료
  indexing           추가 원본/삭제 반영 중; 준비 완료 후 다시 조회
  bootstrap_required 기존 원본의 최초 전체 구축 필요
  capacity_error     구성한 FTS 용량, 디스크 여유 또는 작업 한도 확인 필요
  error              캐시 무결성/처리 오류 확인 필요
pending 건수·바이트·지연은 로그인 사용자의 테넌트 및 허용 인덱스 범위다.
캐시의 준비 여부와 구성 용량은 노드 전체 상태다. 준비되지 않은 동안에도
이미 색인된 원본에 대한 구조화 검색은 사용할 수 있다.

2. 설정 및 기존 원본의 최초 구축

serve 기본 설정: 질의 15초, DuckDB 메모리 한도 512MB, 질의 스레드 4,
FTS 최대 8GiB, 원본 색인 배치 5,000건, 색인 작업 예산 0.25초.
볼륨 여유 하한은 기본 1GiB이며 serve --reserve-gib로 명시할 수 있다.
512MB는 DuckDB 엔진 한도이며 Python·FTS·HTTP를 포함한 프로세스 전체
RSS 제한이 아니다. 실제 프로세스 RSS와 호스트 여유 메모리를 감시한다.

원본 배치는 남은 FTS journal 용량에 맞는 순서상 앞부분만 처리할 수 있다.
설정 배치보다 적게 처리했어도 큐가 남아 있으면 backlog로 판단하여 다음
회차를 0.01초 후 실행한다. 큐가 비었거나 원본 배치가 CapacityError로 중단되면
기존 유휴 대기 설정을 사용한다. 처리 건수만으로 큐가 비었다고 추정하지
않는다. 이 스케줄링은 특정 수집 속도나 수집기 재시도 성공을 보장하지 않는다.

DuckDB OutOfMemoryException은 query_memory_budget 고정 코드의 HTTP 503으로
알린다. 원문 SQL, 로그 본문, 경로 또는 내부 예외 문자열을 응답에 포함하지
않는다. 조회 시간 범위나 반환 필드를 줄여 다시 시도한다. 문법·바인딩·I/O
등 다른 DuckDB 예외를 메모리 부족으로 바꾸지는 않는다.

FTS 배치의 0.25초는 작업을 다음 배치에 양보하는 처리 예산이다. 완료한
문서의 체크포인트와 영속 커밋은 일관된 하나의 단위로 마무리한다. 문서
사이에서 처리 예산 또는 취소를 확인하면 완료한 앞부분을 커밋한다.
파일 동기화 및 SQLite 내부 작업 때문에 배치 전체의 실제 벽시계 시간이
항상 0.25초 이하라는 보장은 없다. 대화형 검색의 제한과 잠금 대기는
별도로 적용하며, 실제 색인 지연·처리 오류·자원 사용량을 함께 확인한다.
각 문서와 체크포인트에는 각각 새로 시작하는 1초의 SQLite VM 중단 한도를
적용한다. 대화형 검색에서는 남은 검색 제한보다 길게 설정하지 않는다.

백그라운드 FTS 작업이 자체 mutex를 처리 예산 안에 얻지 못한 경우에는
다음 회차로 양보한다. 이를 실제 캐시 실패로 기록하거나 이전에 확인한
오류를 지우지 않는다. 대화형 검색의 잠금 기한, 실제 SQLite 오류, 문서
중단, 취소 및 용량 보호는 그대로 적용한다.
문서 처리 중 취소되거나 내부 처리 한도를 넘으면 부분 문서를 게시하지
않고 배치를 롤백·재시도한다. SQLite progress callback은 파일 I/O나 잠금
대기까지 포함한 절대 벽시계 보장이 아니다. 큰 색인에서도 오류 없이
진행되는지는 실제 누적 적재 시험으로 확인한다.

예시(측정한 장비·용량에 맞춰 명시적으로 설정):
  python -m sapientia --data C:\Vatex_LUMINA_xSERA\data serve
    --host 127.0.0.1 --port 8787 --query-timeout 15 --fts-budget-gib 32 --reserve-gib 10
    --indexing-budget 0.5
위 명령은 여러 줄을 설명용으로 나눈 것이다. 실제 실행 시 한 줄로 입력한다.
32GiB로 늘리는 것은 해당 용량/성능의 검증 또는 디스크 확보를 대신하지 않는다.

0.7 이하의 기존 원본, 누락된 캐시, 호환되지 않는 캐시는 전체 초기 구축이
필요할 수 있다. 운영 프로세스를 정상 종료한 후 다음 명령을 실행한다:
  python -m sapientia --data C:\Vatex_LUMINA_xSERA\data rebuild-fts --max-seconds 7200 --fts-budget-gib 32
서비스와 동일 데이터 경로를 사용하는 별도 프로세스는 ProcessLock으로 거부된다.
최초 구축의 별도 예산은 대화형 검색의 15초 제한을 늘리지 않는다. 완성된
캐시만 교체하며 실패한 부분 캐시를 검색 가능 상태로 게시하지 않는다.
FTS journal은 건수/바이트 상한이 있다. 기존 데이터 초기 구축을 미루거나
전문검색 처리가 지속해서 밀리면 원본 색인 ACK도 대기하고 수집 큐의
역압력으로 이어질 수 있다. 서비스 시작 전 유지보수 시간을 계획한다.
전문검색 ready는 진행 중인 원본 인계와 journal 처리가 모두 끝난 상태다.
원본 색인은 journal의 남은 건수·바이트에 맞는 원래 대기열의 앞부분을
선택한다. 막힌 행을 건너뛰지 않고, 최종 용량 검증·원본 커밋·journal 기록·
대기열 ACK의 복구 계약을 유지한다. 완료된 보관 원본의 동일 재전송과,
원본 커밋 후 인계가 중단된 보관 원본을 구분한다. 미완료 인계는 보관
계층으로 이동했더라도 journal 비용을 포함해 전문색인까지 복구한다.
작은 앞부분을 자주 ACK하는 것은 수용 대기시간을 줄이기 위한 처리다.
전문색인의 최대 소비량을 높이거나 무제한 수집을 보장하는 설정은 아니다.
계속되는 수집이 전문 색인 처리량을 넘으면 structured 검색은 가능해도
전문검색은 대기 상태를 반환한다. 단계별 적재 성공을 지속 수집 중의
전문검색 가용성 또는 검색 지연 SLO로 해석하지 않는다.

3. 보관 계층과 무결성

Parquet 파일의 이벤트 식별자는 SQLite의 정확한 복합 기본키 카탈로그로
관리한다. 작은 수집 배치의 중복 검증 때문에 전체 Parquet 키 집합을
매번 읽지 않는다. 파일 영속화, 카탈로그 게시, Hot 원본 정리 및 읽기 뷰
교체는 복구 가능한 순서로 수행한다. Hot/보관 원본의 식별자 불변식이
검증된 경우 UNION ALL을 사용하여 전체 ROW_NUMBER 중복 제거를 피한다.

이전 카탈로그는 일회성 이관 대상이다. 재시작에서 파일 SHA와 카탈로그
키 무결성 확인이 필요하며 대량 보관 시 시작 시간도 측정해야 한다.
성능을 위해 손상 검증을 생략하지 않는다. 동일 ID 재사용, 삭제, 백업 복구,
부분 게시 실패 및 재실행은 별도 회귀 시험 대상이다.
보존 삭제 중인 이벤트 ID는 새 본문으로 다시 수락하지 않는다. 실제 원본
삭제를 확인한 뒤에만 수집 receipt를 삭제한다. 복구 중 hold가 설정되면
원본과 기존 receipt를 함께 보존한다. 구버전/복제 경계에서 held 원본의
receipt가 이미 없으면 원본을 지우거나 새 본문을 수락하지 않고 미완료
상태를 유지한다. 이 상태는 보존 복구 오류를 먼저 해결해야 한다.
미완료 삭제 ID와 보존된 원본 ID는 로컬의 정확한 기본키 카탈로그로
관리한다. 일반 수집마다 과거 보존 이력이나 전체 Hot 원본을 읽지 않는다.
구버전 보존 이력이 있으면 최초 이관에서 실제 남은 원본을 한 번 대조하며,
이관 완료 표시와 카탈로그를 함께 커밋한다. 대량 이력의 이관 시간과
임시 디스크 공간은 업그레이드 유지보수 시간에 포함한다.

storage_footprint는 데이터 디렉터리의 파일 메타데이터를 제한 시간 내에
수집한 캐시다. complete=false는 관측한 일부 용량이며 전체 용량으로
판단하지 않는다. 외부 링크/Windows junction을 따라가지 않는다.
디렉터리 밖의 백업, 할당 블록, 다른 프로그램의 사용량은 포함하지 않는다.
디스크 보호 판단은 실제 볼륨 free space로 수행한다.

4. 재현 가능한 대량 시험

공통 Parquet 작성기는 실제 행 그룹이 16,384행 이하인지 게시 전에 검증한다.
DuckDB 1.5.6의 native batch 허용 오차를 고려하여 COPY 목표는 14,336행으로
낮춘다. 실제 메타데이터가 한도를 넘으면 게시를 거부한다. 파일의 최대
행 수와 행 그룹의 크기는 별개다. 이는 넓은 raw 필드를 여러 스레드가 읽을
때 메모리 사용을 줄이는 설정이며, DuckDB 메모리 한도를 늘리는 설정은
아니다. 기존 파일은 자동으로 바뀌지 않는다. 서버를 정지한 상태에서:

  python -m sapientia --data C:\Vatex_LUMINA_xSERA\data repack-logs --max-files 64 --max-seconds 300 --reserve-gib 10

실제 행 그룹이 한도를 넘는 파일만 기존 파일 게시·SHA·키 카탈로그 교체
절차로 재작성한다. 원문·이벤트 ID·수신 시각·보존 hold와 논리 내용/삭제
세대는 보존한다. 파일 바이트 SHA와 물리 세대는 바뀐다. complete=false는
미완료이며 CLI 종료 코드 2를 반환한다. 같은 명령을 다시 실행하면 남은
파일을 처리한다. 시간 예산은 파일 경계에서 확인하는 협력적 예산이다.
서비스 잠금, 초기 무결성 검사, native 실행 및 파일 동기화의 절대 벽시계
상한을 보장하지 않는다. 검색이나 서비스 시작 시 암묵적으로 재작성하지 않는다.

SPL에서 첫 stats 앞에 search/where/regex만 있고 모든 집계가 순서와 무관한
함수이면 원본 전체에 기본 정렬 순번을 만들지 않는다. first/last/list/values,
latest/earliest 또는 앞선 head/tail/sort/streamstats 등 순서에 의존하는 경로는
기존 순서를 유지한다. 집계 이후 그룹의 주 정렬값이 같으면 그룹 키를 오름차순으로
비교하여 순서를 정한다. 이전에 미정이던 동률 순서를 명시적으로 고정한 변경이다.
DOUBLE 집계의 부동소수점 재결합은 비트 단위 같은 결과를 보장하지 않는다.
시험의 건수·고유 ID·정확 표현 범위 내 정수 합계는 정확히 대조한다.

전체 로그 내보내기는 DuckDB의 JSON 직렬화로 고정 필드와 raw 중첩 값을
만들어 제한된 배치로 디스크에 기록한다. 페이지 API는 JSON 값으로 읽고,
NDJSON/파일 다운로드는 저장한 문자열 그대로 전송한다. 숫자 표기나 이스케이프를
다시 바꾸지 않으므로 전송 바이트의 SHA256 및 Content-Length가 일치한다.
기존 버전에서 만든 snapshot도 저장된 바이트로 내려받는다. 생성·페이지·
다운로드의 사용자/인덱스 권한과 삭제 세대 검증, 시간 및 용량 한도는 유지한다.

tools/qualify_log_platform.py:
  100,000 및 1,000,000건. 기본 15초/별도 120초 질의 제한을 구분한다.
  전체 개수·distinct·숫자 합계·전문검색·전체 snapshot 및 페이지/단일
  다운로드 해시·보관 전환·보존·암호화 백업·복원·손상을 시험한다.
  수집 대기열 설정은 전체/테넌트 각각 150,000건이다.

tools/qualify_log_scale.py:
  독립된 fresh private QA 디렉터리와 검증된 TLS loopback에서 실행한다.
  운영 URL/데이터 경로를 받지 않는다. 두 테넌트 × 세 인덱스, 안정적인
  이벤트 ID/본문, 1MiB 이하 HTTP 배치, 재전송, 50만 건 단위 봉인과
  봉인 후 추가 수집을 포함한다. 1/5/10/25/50백만 건에서 원본의 전체
  개수·distinct·정확한 sequence 합계·타입·범위를 HTTP로 검증한다.
  small 압축하기 쉬운 입력과 realistic 약 1KiB/다양한 키·고유 trace/
  호스트·사용자 입력을 구분한다. 15초마다 RSS·여유 RAM·디스크를 기록한다.
  수집 대기열은 Settings 기본값인 전체 100,000건/테넌트 25,000건이다.
  두 도구의 성공·실패 차이를 입력 크기 하나만의 영향으로 해석하지 않는다.
  scale 도구는 각 50만 건에서 batch=100,000 봉인을 반복한다. 기본 운영
  maintenance는 partition당 batch=5,000이며 retain에서 시간 간격으로 호출한다.
  여섯 eligible partition의 한 회차 최대 30,000건이라는 계산은 특정 구성의
  계산일 뿐 일반 처리량이나 시간당 SLA가 아니다. 시험의 전체 봉인 성공은
  기본 운영 설정의 장기 lifecycle 따라잡기 능력을 검증한 결과가 아니다.
  입력 크기는 실제 보고서의 profile_measurement를 사용한다. small의
  초기 1,000건 표본은 평균 약 270B이며 서버 정규화/FTS/파일 크기와 다르다.
  디스크 10GiB 이상을 남기고 용량 부족을 성공으로 보고하지 않는다.
  원본 무결성, FTS 초기/증분/최종 상태, 재시작 결과는 각각 기록한다.
  FTS 단계에서는 제어 카운터와 별도로 실제 registry/terms 테이블의
  건수 및 테넌트·인덱스 분포를 읽기 전용으로 대조한다. 이 검증 비용은
  별도 기록하며, 서비스의 15초 자원 감시마다 전량을 세지는 않는다.
  cold는 초기 색인 단계 이름이다. OS 캐시를 제거한 검색 시험은 아니며,
  실제 행 수 대조가 뒤이은 검색의 파일 캐시를 데울 수 있다.
  기본 admission-mode=burst8의 짧은 8회 재시도는 과거 실패 재현을 위해
  유지한다. server_backoff는 별도 선택으로, 동일한 이벤트 ID/본문을
  재전송하며 Retry-After를 준수한다. 기본 배치 예산 300초/최대 64회와
  전체 시험 예산을 함께 적용하고, 대기·요청·늦은 ACK를 각각 기록한다.
  이 시험 클라이언트에는 durable outbox가 없으므로 에이전트의 디스크
  스풀이나 생산자 프로세스 장애 복구를 검증한 것으로 해석하면 안 된다.
  fts-observation-timeout은 QA 내부 실제 전량 행 수 대조의 전용 예산이다.
  기본 120초/선택 상한 600초이며 보고서에서 제품 검색 시간과 구분한다.
  query-timeout은 일반 검색에 그대로 적용된다. 관측 방법은 검증된
  internal-content FTS5의 terms_content 실제 행 COUNT와 registry의
  테넌트별 실제 행/인덱스 분포다. 카운터나 MAX(rowid) 추정으로 대체하지 않는다.
  전량 관측이 큰 데이터의 파일 캐시를 데울 수 있고 절대 O(1) 작업이 아니다.

  QA 자원 감시는 client 생성·종료, HTTP 상태/JSON 해석, 자원 한도 검사,
  보고서 저장·출력을 구분한 operation과 허용 목록의 예외 종류·숫자 오류
  코드만 보존한다. 예외 본문·URL·헤더·인증 정보는 기록하지 않는다.
  감시 오류는 시험을 실패시키며, 보고서 저장도 실패하면 메모리의 최초
  실패 상태를 유지한다. 자원 한도 위반 표본과 최초 위반은 저장 오류로
  대체하지 않는다. 자원 관측 실패를 무시하거나 재시도로 성공 처리하지 않는다.
  관측 전용 SQLite 연결은 mode=ro/query_only 및 읽기 트랜잭션을 사용하며,
  별도 threadpool에서 2초 협력적 DB 예산과 100ms busy 대기를 적용한다.
  HTTP 관측 제한은 5초다. 이 예산은 OS I/O의 절대 상한을 보장하지 않는다.
  운영 DB 연결·FTS native 1초/5초·공개 검색 15초/120초·자원 한도는 바꾸지 않는다.
  보고서의 원자 교체에서 Windows 공유/잠금 위반(winerror 32/33)만 최대
  5회, 총 sleep 0.7초 이내로 재시도한다. ACL·용량·fsync·출력 오류는 즉시
  실패하며 기존 checkpoint 파일을 먼저 삭제하지 않는다. 이 보강은 약
  1,100만 건에서 종료된 이전 시험의 원인을 확정한 수정이 아니다. 그
  실패는 원래 예외 종류가 보존되지 않아 telemetry 오류의 구체 원인이 미확정이다.
  무결성 결과에는 검증한 실제 tenant/index 집계의 최소·최대 sequence와
  실제 테넌트 집계 합산값을 보존한다. 예상 수치는 대조 기준이며 실제
  관측 결과를 대신하지 않는다. 과거 실패 보고서는 다시 작성하지 않는다.

FTS 문서 한 건의 native VM 예산은 1초, 완료한 prefix 체크포인트의 예산은
5초로 구분한다. SQLite FTS5는 metadata UPDATE의 statement savepoint에서
앞선 pending terms를 flush하고 내부 병합을 수행할 수 있다. 약 980만 건의
실패 색인 복사본에서는 이 단계의 1초 제한으로 interrupt/rollback이
재현됐다. 체크포인트 예산 변경은 terms·registry·metadata의 동일 트랜잭션과
COMMIT 후에만 journal을 ACK하는 순서를 유지한다. 대화형 요청의 outer
deadline은 두 native 예산 모두를 제한한다. 문서 사이 cancellation은
완료 prefix를 커밋하며, 체크포인트 도중에는 native 예산까지만 지연될 수 있다.
SQLite progress callback이 호출되지 않는 filesystem I/O·busy wait·COMMIT
구간의 절대 벽시계 상한을 뜻하지 않는다. 5초 초과 시에도 미완료 journal을
보존하여 재처리하므로, 이 변경만으로 50M 완료나 영구 진행을 보장하지 않는다.

대규모 도구의 내보내기는 최대 10만 건의 입력 대조 표본이다. 5천만 건
전체 내보내기나 전체 크기 백업의 통과로 해석하면 안 된다. 단일 snapshot
2GiB 및 테넌트별 snapshot 8GiB 한도는 유지되므로 시간/인덱스별로 분할한다.
단일 생산자의 단계별 적재/봉인 시험은 지속 EPS, 동시 검색 SLO, 24시간
soak, 호스트 장애, 복제/고가용성 검증과 별개다. 이 조건 없이 경쟁사와
동급 또는 대기업 운영 준비 완료라고 판정하지 않는다.

보존 retain의 기존 대기 intent 적용, scope 발견, native 후보 조회 및 계층
이동은 서로 다른 작업이다. 내부 10초 반복 예산은 retain 전체의 절대 시간
한도가 아니다. 대량 보존 삭제·hourly 이동이 수집과 검색에 주는 영향은
장시간 운영 부하에서 별도로 측정해야 한다. 50M 단일 노드 시험 설정의
FTS 32GiB·디스크 여유 10GiB·질의 120초는 운영 기본값 8GiB·1GiB·15초와
구분하며, 시험 설정을 운영 기본 용량의 보증으로 해석하지 않는다.
